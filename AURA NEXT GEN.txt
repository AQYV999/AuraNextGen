Bisa banget, dan tetap gampang di-upload ke Firebase Hosting. Firebase Hosting itu cuma nyajiin file statis apa adanya, jadi mau 1 file atau 10 file, cara deploy-nya sama: firebase deploy.

Struktur yang gw sarankan (dari file lu sekarang):

public/
├── index.html      ← cuma kerangka HTML (wajah SVG + UI)
├── style.css       ← semua isi <style>
├── config.js       ← FIREBASE_DB_URL
├── face.js         ← ekspresi, variasi, idle random
├── status.js       ← cekStatus, setStatusOnOff, badge
└── chat.js         ← kirimPertanyaan, renderMarkdown, tungguJawaban

Di index.html, ganti blok <style> dan <script> jadi:

html
<link rel="stylesheet" href="style.css">
...
<script src="config.js"></script>
<script src="face.js"></script>
<script src="status.js"></script>
<script src="chat.js"></script>
<script src="main.js"></script>

Hal yang perlu diperhatikan:

Urutan <script> penting. Karena pakai script biasa (bukan module), file yang dipakai file lain harus dimuat duluan. config.js dulu (isi FIREBASE_DB_URL), lalu face.js (isi faceSvg, terapkanEkspresi, dst), baru status.js dan chat.js yang memanggil fungsi-fungsi itu.
Variabel global dibagi antar file. Di kode lu, ekspresiTerkunci, modeSaatIni, modeDipilih, dll dipakai lintas bagian. Selama semua dideklarasikan di top-level (bukan di dalam fungsi) dan urutan load benar, ini jalan tanpa perubahan.
Baris eksekusi di paling bawah (pilihMode('cloud'); cekStatus(); setInterval(...); mulaiEkspresiOtomatis();) taruh di file terakhir, misal main.js, supaya semua fungsi sudah ter-load sebelum dijalankan.
Deploy-nya tetap simpel:
firebase init hosting   # pilih folder public
firebase deploy

Semua file di folder public/ otomatis ke-upload.

Alternatif kalau mau lebih rapi: pakai ES Modules (<script type="module"> + import/export). Lebih bersih karena nggak ada variabel global bocor, tapi lu harus tambah export/import di tiap file, dan nggak bisa dibuka langsung via file:// (harus lewat server lokal atau Firebase Hosting). Untuk proyek lu yang sekarang, cara script biasa di atas lebih cepat dan minim risiko error.

Satu catatan keamanan: URL Firebase di config.js tetap kelihatan publik (sama kayak sekarang di index.html), jadi rules database tetap perlu diketatkan sebelum lomba, seperti yang udah lu tulis di komentar firebase_client.h.

python
import re
from flask import Flask, request, Response
from piper import PiperVoice, SynthesisConfig
from waitress import serve
from num2words import num2words

app = Flask(__name__)

MODEL_PATH = r"C:\piper\voices\id_ID-news_tts-medium.onnx"

# ===== SETELAN SUARA (ubah-ubah sambil didengar) =====
SYN = SynthesisConfig(
    length_scale=1.25,    # kecepatan: >1 = lebih pelan, <1 = lebih cepat
    noise_scale=0.75,     # variasi nada/intonasi
    noise_w_scale=0.95,   # variasi ritme & jeda antar kata
    volume=1.0,
    normalize_audio=True, # samakan volume antar kalimat
)

JEDA_ANTAR_KALIMAT = 0.28  # detik

print("[Piper] Loading voice model...")
voice = PiperVoice.load(MODEL_PATH)
SR = voice.config.sample_rate
print("[Piper] Model ready. Sample rate:", SR)

JEDA = b"\x00\x00" * int(SR * JEDA_ANTAR_KALIMAT)

def angka_ke_kata(n):
    return num2words(int(n), lang="id")

def bersihkan(t):
    t = re.sub(r"[*#`_]", " ", t)                       # sisa markdown
    t = t.replace("°C", " derajat Celsius").replace("%", " persen")
    # desimal: 28,5 atau 28.5 -> "dua puluh delapan koma lima"
    t = re.sub(r"(\d+)[.,](\d+)",
               lambda m: angka_ke_kata(m.group(1)) + " koma " +
                         " ".join(angka_ke_kata(d) for d in m.group(2)), t)
    t = re.sub(r"\d+", lambda m: angka_ke_kata(m.group(0)), t)
    t = re.sub(r"\s+", " ", t).strip()
    return t

@app.route("/tts", methods=["POST"])
def tts():
    teks = request.get_data(as_text=True).strip()
    if not teks:
        return Response(b"", status=400)

    teks = bersihkan(teks)
    kalimat = [k.strip() for k in re.split(r"(?<=[.!?])\s+", teks) if k.strip()]

    pcm = b""
    try:
        for k in kalimat:
            for chunk in voice.synthesize(k, syn_config=SYN):
                pcm += chunk.audio_int16_bytes
            pcm += JEDA
    except Exception as e:
        print(f"[TTS] Error: {e}")
        return Response(b"", status=500)

    print(f"[TTS] {len(kalimat)} kalimat, '{teks[:50]}' -> {len(pcm)} bytes PCM")
    return Response(pcm, mimetype="application/octet-stream")

if __name__ == "__main__":
    print("Server berjalan di port 5002...")
    serve(app, host="0.0.0.0", port=5002)

Untuk bahasa Indonesia yang benar-benar offline, pilihannya memang sempit. Voice Indonesia di Piper cuma satu, yaitu “News”, dan itu yang sekarang lu pakai. Jadi lewat Piper tidak ada model Indonesia lain yang bisa dipilih. 
tts

Di luar Piper ada beberapa opsi, dengan catatan jujur dari gw:

MMS-TTS Indonesia (facebook/mms-tts-ind, dari Meta): model offline yang memang mendukung bahasa Indonesia. Gw tidak mau janji kualitasnya lebih bagus dari Piper, karena setahu gw kelasnya mirip (sama-sama jenis VITS), cuma karakter suaranya beda. Layak dicoba kalau lu penasaran, tapi jangan berharap lompatan besar. Butuh library transformers dan torch, jadi ukurannya lebih berat dari Piper.
Suara bawaan Windows (SAPI, misal “Microsoft Andika”): offline dan gampang, tapi biasanya lebih kaku dari Piper.
Model besar seperti XTTS: setahu gw tidak mendukung bahasa Indonesia secara resmi, jadi tidak gw sarankan.

Jadi realistisnya, untuk offline murni, Piper yang lu pakai sudah pilihan terbaik yang praktis. Peningkatan terbesar sekarang datang dari hal lain:

Setelan dan pembersihan teks (sudah lu pasang): angka jadi kata, jeda antar kalimat, length_scale.
Gain digital di ESP32: turunkan GAIN_DIGITAL_TTS dari 5.0 ke sekitar 1.5-2.0. Dari catatan gw, nilai 5.0 bikin clipping, dan itu penyebab suara serak yang sering disalahkan ke model.
Speaker: unit 3W di enclosure tertutup membatasi kejernihan dan bass, apa pun modelnya.
Jalur ElevenLabs yang sudah ada di AURA: itu kualitas terbaik yang lu punya sekarang. Kalau internet pasti ada saat demo, lu bisa balik urutannya: ElevenLabs sebagai utama, Piper sebagai cadangan offline. Di tts_local.h itu tinggal atur flag ttsPakaiLokal.

Bisa, dan lu nggak perlu ganti-ganti manual lagi. Masalahnya cuma IP laptop berubah tiap pindah WiFi (DHCP), sementara serverAI di kode lu hardcode 192.168.1.100. Ada beberapa cara, gw urutin dari yang paling cocok buat setup lu:

1. Laptop “lapor” IP-nya ke Firebase (paling aman)
Lu udah pakai Firebase, jadi tinggal tambah satu node /server_ip. Script kecil di laptop ngirim IP-nya tiap berubah, ESP32 baca dari situ sebelum nembak Ollama/TTS lokal. Syaratnya cuma ESP32 dan laptop satu jaringan, dan itu emang syarat mode local.

Di laptop (Python, jalankan bareng Ollama):

python
import socket, requests, time

URL = "https://aura-monitoring-859d9-default-rtdb.asia-southeast1.firebasedatabase.app/server_ip.json"

def ip_lokal():
    s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    s.connect(("8.8.8.8", 80))
    ip = s.getsockname()[0]
    s.close()
    return ip

terakhir = ""
while True:
    ip = ip_lokal()
    if ip != terakhir:
        requests.put(URL, json=ip)
        terakhir = ip
    time.sleep(10)

Di ESP32 (taruh di firebase_client.h, karena FIREBASE_DB_URL didefinisikan di situ):

cpp
String ipServerLokal = "";

bool cariIPServerLokal() {
  if (WiFi.status() != WL_CONNECTED) return false;
  HTTPClient http;
  http.begin(String(FIREBASE_DB_URL) + "/server_ip.json");
  if (http.GET() != 200) { http.end(); return false; }
  String p = http.getString();
  http.end();
  p.replace("\"", ""); p.trim();
  if (p == "null" || p.length() < 7) return false;
  ipServerLokal = p;
  return true;
}

Apa pun pilihannya, pastikan dua hal ini di laptop, karena sering jadi penyebab “kok nggak nyambung”:

Penyebab paling mungkin
Audio diputar sambil jaringan/loop lain jalan. updateFirebase() bikin HTTP request blocking tiap 3 detik, ditambah radar.check() dan delay(50). Kalau pemutaran audio nebeng di loop(), buffer I2S bakal kosong (underrun) tiap ada request, dan itu kedengeran putus-putus.
DMA buffer terlalu kecil. dma_buf_count = 8 dan dma_buf_len = 256 cuma nahan sekitar 128 ms audio di 16 kHz. Gangguan WiFi sebentar aja sudah bikin buffer habis.
Memori mepet. Respons TTS jadi base64 (~213 KB per 5 detik suara), sedangkan DynamicJsonDocument(200000) hampir menghabiskan heap ESP32 tanpa PSRAM. Ini bikin gagal atau audio kepotong.
Header WAV ikut dimainkan. TTS LINEAR16 mengembalikan header 44 byte. Kalau ikut ditulis ke I2S, hasilnya bunyi “tek/klik” di awal.
Power speaker. MAX98357A butuh 5V yang stabil. Kalau dari pin 3V3 atau USB yang lemah, suara pecah/putus waktu volume naik.
Perbaikan, urut dari yang paling berdampak

Prioritas 3 lebih tinggi dari loop biasa, jadi nggak keganggu.

2. Download full dulu, baru putar. Jangan streaming sambil download. Selama audio main, pause updateFirebase() (kasih flag sedangBicara).

3. Pecah jawaban per kalimat. TTS per kalimat (~2-3 detik), putar berurutan. Heap aman, dan tiap potongan kecil jadi nggak gampang gagal. Jawaban Gemini lu sudah dibatasi 300 token, jadi cocok.

4. Cek heap sebelum TTS: kalau ESP.getFreeHeap() < 80000, jangan request. Kalau board lu punya PSRAM, aktifkan dan alokasikan buffer audio pakai ps_malloc().

5. Hardware: MAX98357A ke 5V, tambah kapasitor 100-470 µF dekat pinnya, kabel I2S pendek, dan jauhkan dari antena WiFi.

Soal target 95%

Biar bisa diukur, hitung underrun: kalau i2s_write dengan timeout kecil (misal 100 ms) sering return kurang dari n, itu tanda buffer kosong. Catat jumlahnya per kalimat, dan target lu: kurang dari 1 dari 20 kalimat yang putus.

Oke, berarti ElevenLabs pcm_16000 yang di-stream langsung ke I2S. Penyebab patah-patahnya beda dari yang gw bahas tadi (itu soal Google TTS, abaikan).

Kenapa stream langsung ke I2S bikin patah

Audio PCM 16 kHz 16-bit butuh 32 KB/detik, terus-menerus. Kalau tiap chunk dari jaringan langsung ditulis ke I2S, kecepatan putarnya ikut kecepatan download. Sekali WiFi/hotspot macet 100-300 ms (sering banget di hotspot HP/laptop), DMA buffer lu yang cuma ~0.32 detik habis, lalu suaranya putus. tx_desc_auto_clear cuma bikin hening, bukan bikin lancar.

Fix paling ngaruh: pre-buffer + ring buffer + 2 task
Task download (core 0 atau 1) baca stream ElevenLabs, masukin ke ring buffer.
Task putar (priority lebih tinggi) ambil dari ring buffer, tulis ke I2S.
Jangan mulai putar sebelum buffer terisi ~1-1,5 detik (32-48 KB). Itu yang nyerap jitter jaringan.
cpp
#include "freertos/ringbuf.h"
RingbufHandle_t rb = xRingbufferCreate(64 * 1024, RINGBUF_TYPE_BYTEBUF); // 64KB ~ 2 detik

// task download: baca http stream -> xRingbufferSend(rb, buf, n, portMAX_DELAY);
// task putar:
//   tunggu sampai terisi >= 40KB (prebuffer), baru mulai
//   size_t n; void* d = xRingbufferReceiveUpTo(rb, &n, pdMS_TO_TICKS(200), 2048);
//   i2s_write(...); vRingbufferReturnItem(rb, d);

Kalau sudah dapat semua byte tapi masih ada sisa buffer, biarkan task putar menghabiskannya. Jangan di-cut.

Perbaikan pendukung
Stop polling saat bicara. Pas audio main, pause /suara (2 dtk), /status (3 dtk), dan /histori. Tiap HTTPS request itu makan CPU dan bandwidth WiFi dan ganggu stream. Pakai flag sedangBicara.
Baca stream dengan chunk besar (stream->readBytes(buf, 1024..2048)), jangan 1 byte-1 byte atau String.
Task putar jangan sama core dengan WiFi (core 0). Taruh di core 1, priority 3-4. Task download juga jangan di-delay lama.
DMA lebih besar: coba dma_buf_count = 8, dma_buf_len = 1024 (sekitar 0,5 detik). Ini bonus, bukan solusi utama.
Jaringan: kalau pakai hotspot Windows (192.168.137.x), jitter-nya biasanya lebih parah dari router. Cek RSSI, kalau di bawah -70 dBm ya bakal patah apa pun kodenya.
Gain 3.0 digital bisa bikin clipping yang kedengeran seperti “patah/pecah” padahal bukan underrun. Tes turun ke 2.0 dulu untuk bedain keduanya.
Kalau pakai ESP32-S3 N16R8 nanti, taruh ring buffer di PSRAM dan bisa gede (256 KB+), jadi hampir kebal jitter.
Cara bedain penyebabnya

Tambah log di task putar: hitung berapa kali ring buffer kosong waktu lagi main. Kalau sering kosong → masalah jaringan/buffer (solusi di atas). Kalau nggak pernah kosong tapi masih pecah → clipping gain atau power MAX98357A (harus 5V, jangan 3V3).

  String promptLengkap = String(KEPRIBADIAN_AURA_LOKAL) + "\n\n"

                       + susunKonteksKamarLokal();

  HTTPClient http;
  http.begin(serverAI);
  http.addHeader("Content-Type", "application/json");
  http.setTimeout(60000);

  JsonDocument doc;
  doc["model"] = "qwen3:8b";
  doc["prompt"] = promptLengkap;
  doc["stream"] = false;

  String data;
  serializeJson(doc, data);

  Serial.printf("[LocalAI] POST ke %s, payload %d bytes\n", serverAI, data.length());

  int code = http.POST(data);

  if (code <= 0) {
    Serial.printf("[LocalAI] Koneksi gagal: %s\n", http.errorToString(code).c_str());
    http.end();
    return false;
  }

  if (code < 200 || code >= 300) {
    Serial.printf("[LocalAI] HTTP error %d\n", code);
    Serial.println(http.getString());
    http.end();
    return false;
  }

  String respon = http.getString();
  http.end();

  JsonDocument respDoc;
  DeserializationError err = deserializeJson(respDoc, respon);
  if (err) {
    Serial.printf("[LocalAI] JSON parse error: %s\n", err.c_str());
    Serial.println(respon);
    return false;
  }

  jawaban = respDoc["response"].as<String>();
  jawaban.trim();

  if (jawaban.length() == 0) {
    Serial.println("[LocalAI] Jawaban kosong dari Ollama");
    return false;
  }

  Serial.printf("[LocalAI] OK, %d karakter\n", jawaban.length());
  return true;
}

buka speaker salah gw gw mau nyalain mic

Setting up microphone input with proper I2S configuration.

Oke, mic berarti. Mic INMP441 pakai I2S_NUM_0, speaker I2S_NUM_1, jadi nggak bentrok dan bisa nyala barengan.

Cek wiring dulu:

VDD ke 3.3V, GND ke GND
SD ke GPIO32, SCK ke GPIO14, WS ke GPIO19
Pin L/R ke GND. Kodenya pakai I2S_CHANNEL_FMT_ONLY_LEFT, jadi kalau L/R floating atau ke VCC, datanya bakal nol terus.

Di AURA-Last.ino:

cpp
// include (pastiin nggak ke-comment)
#include "mic_recorder.h"

// di setup(), sebelum WiFi.begin()
inisialisasiMic();
statusMic = true;   // biar dashboard nampilin Mic: ON

Pastikan bool statusMic dideklarasi sebelum include-nya, seperti di versi lama.

Tes cepat (taruh di mic_recorder.h atau di .ino, panggil dari setup() sekali):

cpp
void tesMic() {
  static int16_t buf[512];
  size_t dibaca = 0;
  Serial.println("[Mic] Tes 3 detik, coba ngomong/tepuk tangan...");
  unsigned long mulai = millis();
  while (millis() - mulai < 3000) {
    i2s_read(I2S_NUM_0, buf, sizeof(buf), &dibaca, 100);
    int n = dibaca / 2;
    int peak = 0;
    for (int i = 0; i < n; i++) peak = max(peak, abs((int)buf[i]));
    Serial.print("Peak: ");
    Serial.println(peak);
    delay(100);
  }
}

Bacanya:

Peak naik pas lo tepuk tangan: mic hidup, aman.
Peak 0 terus: hampir pasti wiring, biasanya L/R atau SD.
Peak naik tapi kecil banget (di bawah ~200 meski ngomong dekat): INMP441 sebenarnya ngeluarin data 24-bit di slot 32-bit, jadi mode 16-bit sering bikin suara pelan. Solusinya ganti bits_per_sample ke I2S_BITS_PER_SAMPLE_32BIT, baca ke buffer int32_t, lalu geser >> 14 sebelum dipakai. Kalau kejadian, kabarin dan gue bikinin versi 32-bit-nya.

Satu catatan: rekamAudio() pakai portMAX_DELAY, jadi kalau mic nggak ngirim data, dia bakal hang selamanya. Makanya tes pakai timeout 100 ms di atas, dan jangan langsung panggil rekamAudio() buat tes pertama.

Mode siang dan malam otomatis. Dari jam RTC atau data cahaya. Malam dibuat lebih redup dan hangat. Itu juga sekalian nunjukin bahwa data sensornya kepakai.

Panel dan kartu
5. Panel sensor jadi kartu dengan ikon. Sekarang berupa daftar teks kecil. Ganti jadi kartu mini: termometer dengan bar warna (biru dingin ke merah panas), tetesan buat kelembapan, ikon orang berdenyut kalau radar mendeteksi, dan titik hijau atau merah buat Mic, OLED, RTC.
6. Gauge melingkar. Suhu dan kelembapan dibuat cincin progres kecil yang isinya berubah halus. Lebih enak dilihat daripada angka doang.
7. Sparkline mini. Garis tren 30 menit terakhir di bawah angka suhu, jadi gak perlu buka panel Tren buat lihat arah perubahan.
8. Panel kanan bisa dilipat jadi ikon. Waktu presentasi, wajah bisa tampil bersih tanpa panel.

Chat dan interaksi
9. Bubble chat lebih hidup. Jawaban muncul dengan efek mengetik, dan lencana mode (Cloud/Local/Standalone) berwarna di tiap jawaban. Sekarang labelnya cuma teks.
10. Chip pertanyaan cepat di atas chat bar, misalnya “Ruangan nyaman?” atau “Ada orang?”.
11. Visualizer suara waktu AURA bicara. Gelombang dari tengah wajah, bukan cuma lencana kecil.
12. Sentuhan mikro. Tombol kirim yang berubah jadi animasi loading, haptic getar di HP, dan wajah yang menoleh ke arah kursor atau sentuhan.

Kerapian tipografi
13. Satu font khusus. Pasangan font display buat judul dan angka (mirip gaya dashboard futuristik), plus font angka monospace buat suhu dan jam supaya lebarnya stabil waktu berubah.
14. Konsistensi jarak dan radius. Samakan sudut, jarak, dan tebal garis semua panel supaya kelihatan satu desain, bukan tempelan.

Sekarang isinya daftar teks kecil, label kiri dan angka kanan:

Suhu / Temp        28.5°C
Lembab / Humid     62%

Radar              Orang bergerak, jarak 120 cm

Semuanya sama kecil dan sama warna, jadi mata gak tahu harus lihat ke mana. Juri butuh baca satu-satu.

Idenya, tiap sensor jadi kartu mini yang punya ikon dan indikator visual sendiri:

Suhu: ikon termometer dan bar tipis di bawah angka. Biru kalau dingin, hijau kalau nyaman, oranye ke merah kalau panas. Jadi tanpa baca angka pun kelihatan ruangannya panas atau enggak.
Kelembapan: ikon tetesan air dan bar isi yang naik turun sesuai persen.
Radar: ikon orang yang berdenyut atau punya gelombang kalau ada yang terdeteksi, dan abu-abu diam kalau kosong. Teks panjang “Orang bergerak, jarak 120 cm” jadi keterangan kecil di bawahnya.
Cahaya: ikon matahari atau bulan.
Mic, OLED, RTC: tiga titik kecil sebaris. Hijau kalau ON, abu-abu atau merah kalau OFF, dengan label kecil di bawahnya.
